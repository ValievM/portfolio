# ADR 0005: домен разговора

**Реализация (2026-09-25):** T8 типизированные `CallId`/`ItemId` сделан (в `main`), T9 sealed-состояние хода `TurnState` сделан (в `main`, `:core:domain`, `transitionTurn`). T7 (`ConversationSession`, `conversationId`, миграция Room v1→v2) отложен: владелец пока не планирует несколько чатов, решение ждёт.

Статус: **принято** 2026-09-24 (владелец продукта делегировал решение тимлиду). Код в этом ADR не менялся; основа: main `9f04c86`, пачки подтверждений (ADR 0004) уже в main.

## Контекст

История, активный ход, отмена, повтор и обработка собственных эмиссий Room сейчас собраны в `ChatViewModel` ([`ChatViewModel.kt:36–63, 66–100, 130–220`]). Порт и Room-репозиторий адресуют одну глобальную историю; сущность имеет первичный ключ только по позиции ([`Repositories.kt:6–12`], [`ConversationEntity.kt:6–19`], [`ConversationDao.kt:10–31`]).

## Решение

1. В `:core:domain` ввести `CallId` и `ItemId` как value class; идентификаторы в порте истории назвать явно: `callId` — для вызова, `itemId` — для элемента провайдера/истории. Не выводить назначение из префикса строки.
2. Представлять фазу хода одним sealed-состоянием. `Idle`, `Running`, `AwaitingApproval`, `Stopped`, `Interrupted` и две ветви `Failed` заменяют независимые `isRunning/error/canRetry`. Ошибка хранилища остаётся отдельным состоянием синхронизации.
3. Разместить `ConversationSession` в `:app` как небольшой координатор приложения, а не переносить I/O-оркестрацию в `:core:domain`. Он владеет состоянием истории, активным Job, retry, порядком записей и принятием чужих эмиссий; `ChatViewModel` переводит его состояние/события в UI. Все команды изменения истории, включая очистку из настроек, идут через сессию.
4. Добавить `ConversationId` и передавать его через `ConversationRepository`; значение по умолчанию `default` сохраняет текущий сценарий. Room v2 использует составной ключ (conversationId, position), существующие строки получают `default`.

## Почему не `:core:domain`

| Размещение | Плюсы | Минусы |
|---|---|---|
| `:core:domain` | Чистый Kotlin; удобно повторно использовать переходы состояния | Сессия координирует долгоживущий Job, поток Room-наблюдения, сериализацию записи и вызов `AgentLoop`; это application service, замаскированный под доменную сущность |
| `:app` — выбрано | Здесь уже собираются Room, DI, `AgentLoop` и пользовательские команды; не нужен новый модуль | Нельзя привязывать правила к Compose/Android. Типы `ConversationId`, `ItemId`, `CallId` и sealed-модель хода остаются в чистом domain |

Термин «агрегат разговора» описывает границу согласованности и команд. В строгом DDD сессия, управляющая репозиторием и исполнением, является координатором приложения, а не богатым domain aggregate. Выделять `:core:application` следует только при появлении второго реального runtime-потребителя.

## Последствия и риски

- UI и настройки используют одну сессию для текущего `ConversationId`; очистка сначала отменяет и дожидается активный ход, затем очищает только выбранный разговор.
- Новая схема требует миграции Room v1→v2 и теста со старым файлом БД. `exportSchema` сейчас выключен; базовую схему v1 нужно сохранить до изменения сущности.
- Retry после смерти процесса может повторить уже выполненный инструмент, если процесс умер до сохранения результата. Повтор остаётся только явным действием пользователя; exactly-once для внешнего эффекта эта схема не обещает. Точное окно зависит от момента завершения инструмента: [проверить].
- Подтверждения ветки `feat/batch-approval` входят в модель как один `AwaitingApproval` с точным упорядоченным набором `CallId`. Отмена/смерть процесса не сохраняет ответ подтверждения; пакет не исполняется без текущего ответа. Поддержка `parallel_tool_calls` реальным бэкендом не подтверждена: [проверить].

Подробные типы, переходы, миграция и план коммитов: [проектирование эпика](../architecture/conversation-domain-design.md).

## Решения по открытым вопросам (2026-09-24)

1. **Stop без немедленного Retry:** да. «Стоп» — осознанное действие, повтор не предлагаем; состояние `Stopped` отдельное.
2. **Downgrade Room:** не поддерживаем и не блокируем специально; фиксируем «откат версии приложения не поддерживается». Вернуться к вопросу, когда появится больше одного разговора.
3. **DismissError:** закрывает сообщение и снимает Retry (как сейчас): закрыл значит отказался от повтора.
4. **Идемпотентность (exactly-once):** не вводим. `CONFIRM`-инструменты переспрашивают подтверждение при повторе, остальные безобидны. Ключи идемпотентности возвращаем вместе с `SENSITIVE`-инструментами (SMS, звонки).
5. **Размещение сессии:** `ConversationSession` в `:app` без импортов Android и Compose (проверять правилом Konsist), чтобы при агенте без UI её можно было перенести пакетом.
6. **Тест миграции Room:** зависимость `androidx.room:room-testing` (только для тестов, версия та же, что у Room) разрешена для шага T7; без неё реальную миграцию со старым файлом БД не проверить. Схема v1 уже сохранена в `app/schemas` (ветка `feat/room-schema`).
