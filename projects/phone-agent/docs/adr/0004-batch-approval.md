# ADR 0004: одно подтверждение на пачку вызовов

## Контекст

Пользователь просит «поставь 5 будильников», и на каждый будильник приходила отдельная шторка подтверждения. Причина в двух местах. В запросе к модели стояло `parallel_tool_calls: false`, поэтому модель просила по одному вызову за ответ (и упиралась в лимит шагов `maxSteps = 5`). Кроме того, `ToolPipeline` спрашивал подтверждение отдельно для каждого вызова.

## Решение

1. **Запрос:** `parallel_tool_calls: true`, чтобы модель могла вернуть несколько вызовов в одном ответе. Это константа бэкенда (`docs/backend-notes.md`); проверена на живом бэкенде 2026-09-24 (запрос принят, пачка из 3-4 вызовов); при отказе бэкенда откат — вернуть `false`.
2. **Порт:** в `UserInteraction` добавлен `confirmBatch(requests): Boolean`, один вопрос на всю группу: `true` разрешает все вызовы, `false` отклоняет все («всё или ничего»).
3. **Конвейер:** `ToolPipeline.batchGroups(calls)` выбирает вызовы одного ответа с риском `CONFIRM` и корректными аргументами и режет их на группы не больше `maxBatchSize` (по умолчанию 15); группа из одного вызова пачкой не считается и подтверждается как раньше. `SENSITIVE` в пачки не попадают: для них по документу нужно подтверждение с деталями по одному. `ToolPipeline.run(..., approval)` принимает готовый ответ (`GRANTED`/`DECLINED`) вместо повторного вопроса; валидация аргументов идёт раньше и от ответа не зависит.
4. **Цикл агента:** `AgentLoop` заранее строит описания всех вызовов группы. Только если все они готовы, агент показывает карточки, эмитит `BatchApprovalRequested` и задаёт один вопрос; затем выполняет вызовы по очереди. Если описание хотя бы одного вызова не построилось, вопрос не показывается, ни один вызов не запускается, а `function_call_output` объясняет, что пачку не показывали и не выполняли — модель не принимает это за отказ пользователя. При обычном подтверждении модель получает `function_call_output` на каждый `call_id` в прежнем порядке.
5. **UI:** `BatchApprovalSheet` показывает список строк из `CallDescription` каждого вызова (не из текста модели) и кнопки «Разрешить все» / «Отклонить все»; жест «назад» = отклонить все.

## Рассмотренные альтернативы

- «Разрешить все будильники в этом запросе» на первой шторке: отклонено — пользователь не видит следующие вызовы до их выполнения.
- Выбор отдельных вызовов в списке: отложено — сложнее интерфейс и состояния, для MVP хватает «всё или ничего».
- Пачки для `SENSITIVE`: отклонено — противоречит требованию подтверждения с деталями по одному вызову.

## Последствия

- Изменился публичный порт `UserInteraction`: все реализации и фейки обязаны иметь `confirmBatch`.
- Длинный список можно подтвердить не читая, поэтому лимит 15 и время каждого будильника отдельной строкой.
- Если бэкенд не поддерживает несколько вызовов за ответ, приложение работает как раньше (по одному вызову, обычная шторка), пачка просто не формируется.
- В смешанной пачке (`SAFE` + `CONFIRM` в одном ответе) карточки группы появляются раньше карточек `SAFE`-вызовов, порядок выполнения при этом сохраняется.
