# Трекер задач (GitHub Issues)

> См. также: [AGENTS.md](../../AGENTS.md) · [OWNER-TASKS.md](../../OWNER-TASKS.md) · [этапы](../stages/README.md) · [ручные проверки](../manual-verification.md) · [CI](ci.md)

Все задачи проекта ведём в Issues приватного репозитория `ValievM/phone-agent`: <https://github.com/ValievM/phone-agent/issues>. Спецификация задачи лежит в issue, а не в чате: она не пропадает, когда контекст разговора сжимается, а промпт агенту получается коротким.

## Что где живёт (чтобы не было двух правд)
| Что | Где | Кто меняет |
|---|---|---|
| Работа: что сделать, тест-кейсы, границы | issue | Claude заводит и закрывает |
| Приёмка этапа | чекбоксы в `docs/stages/*.md` | `[x]` только после проверки; пункт этапа не дублируется в issue, issue на него ссылается |
| Проверка на телефоне | `docs/manual-verification*.md` | `[x]` ставит только владелец |
| Что ждёт владельца | фильтр `who:owner` и выжимка в `OWNER-TASKS.md` | Claude |

## Метки
| Группа | Метки | Смысл |
|---|---|---|
| Кто | `who:owner`, `who:gpt1`, `who:gpt2`, `who:gpt3`, `who:claude` | Кто сейчас должен действовать |
| Статус | `status:ready`, `status:doing`, `status:review`, `status:waiting-owner`, `status:blocked` | Где задача. Нет метки статуса: бэклог |
| Срок | `mvp`, `post-mvp` | Нужна ли для MVP |
| Вид | `decision`, `phone-check`, `bug`, `enhancement`, `documentation`, `chore` | Что за задача |

Задача закрыта, значит слита в `dev` (или отклонена). Отдельной метки «готово» нет.

## Жизненный цикл
1. **Заведение.** Цель, тест-кейсы (по правилу из [AGENTS.md](../../AGENTS.md)), что читать, границы, «готово, когда». Шаблон: `.github/ISSUE_TEMPLATE/task.yml`.
2. **`status:ready`.** Задача готова к выдаче. Claude держит под каждого агента минимум одну-две такие, чтобы агент не простаивал: сдача пришла, следующая выдаётся сразу.
3. **`status:doing`.** Claude даёт агенту промпт (шаблон ниже). Агент работает в своём worktree и ветке, отчёт по шаблону из issue.
4. **`status:review`.** Claude ревьюит полностью: код, тесты, мутационные проверки, полный `./gradlew check` на слитом результате.
5. **Слияние.** Ветка задачи вливается в `dev` после ревью и полного `check` (решает и делает Claude), коммит слияния с `Closes #N`. `dev` вливается в `main`, когда зелёные `check` и CI и владелец проверил сборку на телефоне.
6. **Решения владельца.** `who:owner` + `decision` + `status:waiting-owner`. Владелец отвечает комментарием одним словом, Claude выполняет и меняет метки.

Кто что делает на GitHub: **все три GPT работают роем** ([swarm.md](swarm.md)) и сами ведут метки `who:`/`status:` и комментарии в своих issues с префиксом `[GPT-1]`, `[GPT-2]` или `[GPT-3]`. Закрывает issues и вливает ветки только Claude, он же решает все вопросы реализации. Владелец проверяет результат и в issues по реализации не участвует.


## Ветки (git flow)
- `main`: только проверенное. Обновляется из `dev` быстрой перемоткой или merge, когда зелёные `check` и CI на `dev` и владелец проверил сборку на телефоне. Из `main` собирается релиз, от него ставится тег `vX.Y.Z`.
- `dev`: интеграция. Сюда Claude вливает ветки задач после ревью и полного `check`. Перед каждым вливанием CI на `dev` должен быть зелёным.
- `<тип>/<N>-<слово>` (feat, fix, chore, docs, refactor): одна задача, живёт от `dev` до вливания в `dev`, потом удаляется. Работает агент в своём worktree.
- Срочная правка `main`: ветка `hotfix/<N>-<слово>` от `main`, вливается в `main` и сразу в `dev`.
- Запрещено всем, включая Claude: force-push, переписывание истории `main` и `dev`, коммит напрямую в них (кроме документов процесса).
## Ветки и коммиты
- Ветка `<тип>/<номер>-<слово>`: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`. Worktree в `/Users/valiev/phone-agent-worktrees/`.
- Коммит агента: `Refs #N`. Коммит слияния: `Closes #N`.
- Пуш на GitHub только по слову владельца («пушь»), перед ним проверка коммитов на секреты.

## Промпт агенту
**Промпт полный и самодостаточный, чем подробнее, тем лучше: не сокращать до ссылки на issue.** Агент не должен догадываться и не должен зависеть от доступа к GitHub. Промпт = шапка (правила, ниже) + текст задачи + шаблон отчёта (ниже). Текст задачи это тело issue дословно, поэтому issue пишется сразу как полное описание: ветка и worktree, цель, проблема с файлами и строками, алгоритм или требования, тест-кейсы, доказательство мутацией, что менять и что нет, документы, «готово, когда», «на чём остановиться и спросить». Пример полноты: issue «Контекст запроса целыми ходами».

Начало шапки зависит от исполнителя:
- GPT: «Ты исполнитель-архитектор в проекте phone-agent (…). Прочитай AGENTS.md целиком, затем файлы из раздела «Что прочитать» в задаче.»

Общие правила шапки (для обоих):
```text
## Правила (жёсткие)
- Папку /Users/valiev/phone-agent НЕ трогай (без правок и checkout). Для задачи свой worktree: git worktree add /Users/valiev/phone-agent-worktrees/<имя> -b <ветка> dev, затем скопируй в него local.properties из /Users/valiev/phone-agent.
- Ветки от dev. В dev и main не коммить, не мёржь, не пушь. Одна задача = одна ветка = 1-3 маленьких коммита, в конце сообщения Refs #N.
- Перед КАЖДЫМ коммитом по порядку: ./gradlew :app:kspReleaseKotlin :tools:kspReleaseKotlin, ./gradlew spotlessApply, ./gradlew check и python3 scripts/check_docs.py. Читай вывод целиком. Пока что-то красное, не коммить.
- TDD для логики: красный тест (покажи, что упал по нужной причине), минимальный код, зелёный вывод. Тест-кейсы из задачи пиши сразу и показывай в отчёте. Тесты не ослаблять, не удалять, не @Ignore. Существующий тест менять только если это прямо разрешено в задаче, иначе остановись и спроси.
- Доказательство мутацией для каждого нового теста с логикой: сломай код, покажи красный, верни исправление.
- Новых зависимостей, модулей, разрешений и паттернов без вопроса нет. Секретов в diff нет. [x] в чек-листах не ставить (это делает владелец). Файлы docs до 14336 байт, новые регистрировать в docs/README.md.
- Если задача противоречит коду или документам: остановись и спроси в отчёте, не выбирай молча.
- Кончаются токены: заверши шаг так, чтобы ветка оставалась зелёной, пришли отчёт, остановись.
- Задача записана в issue #N (gh issue view N); текст в промпте совпадает с ним, при расхождении верь issue.
```

Шаблон отчёта (в конце промпта): 1) ветка, worktree, хеши коммитов; 2) что изменено по файлам и зачем; 3) тест-кейсы «имя → что проверяет», красный и зелёный вывод; 4) доказательство мутацией; 5) результат `check` и `check_docs.py`; 6) что не проверено; 7) риски и наблюдения по ходу; 8) вопросы и решения, нужные от владельца.

Claude собирает промпт из issue и этой шапки. Для работы роя есть готовый универсальный промпт [swarm-prompt-gpt.md](swarm-prompt-gpt.md), персональные файлы для каждого GPT лежат в `.prompts/` (см. [swarm.md](swarm.md)).

## Доска (по желанию)
Колонки по статусам можно добавить через GitHub Projects. Нужно один раз выдать `gh` право на проекты: `gh auth refresh -s project -h github.com` (это делает владелец). Без доски всё работает списком с метками.

## Чего не делаем
- Не заводим issue на каждую мелочь и не дублируем в них чек-листы этапов.
- Не кладём в issues токены, ключи и данные из чатов, даже в приватном репозитории.
- Не меняем смысл задачи молча: изменился объём, пиши комментарий в issue.
