# Паттерны, конкурентность, DI

> См. также: [обзор](overview.md) · [ядро](core.md)

## Паттерны: где, зачем, когда вводим

| Паттерн | Где | Зачем | Когда вводим |
|---|---|---|---|
| Ports & Adapters | границы ядра | замена реализаций, тесты без Android | день 1 |
| Dependency Rule | все модули | ядро не ломается снаружи | день 1 |
| Composition Root + DI (Hilt) | `:app` | вся сборка в одном месте | день 1 |
| UDF / MVI-lite | UI | предсказуемое состояние | день 1 |
| Repository | данные | один источник правды на тип данных | этап 5 (история), настройки раньше |
| Конечный автомат | `AgentLoop` | понятные состояния, тесты | этап 4 |
| Strategy | `AuthProvider`, `BackendProfile`, `ContextWindowPolicy`, `ApprovalPolicy` | подмена поведения без `if` | по мере появления |
| Registry / Plugin (multibinding) | `Tool`, `AuthProvider` | расширение без правки ядра | этап 4 |
| Middleware (chain of responsibility) | `ToolPipeline` | сквозные правила для всех инструментов | этап 4 |
| Anti-Corruption Layer | `:data:llm` | изоляция нестабильного бэкенда | этап 3 |
| Decorator / Interceptor | OkHttp (`Auth`, логи) | токены и редактирование логов вне логики | этап 2-3 |
| Single-flight (mutex) | обновление токена | один refresh на всех | этап 2 |
| Humble object | Android API в `:tools` | логика тестируется без устройства | этап 4 |
| Mediator / bridge | `UserInteractionBridge` | ядро спрашивает пользователя, не зная UI | этап 4 |
| Result-as-data (sealed) | ошибки, `ToolOutcome` | нет скрытых исключений | день 1 |
| Test doubles (фейки) | `testFixtures` | быстрые детерминированные тесты | день 1 |

**Когда НЕ применять:** Strategy для одной реализации (пока не нужна вторая, оставляем интерфейс и одну реализацию, без фабрик); Repository над тем, что просто читается один раз; Mediator там, где хватает обычного вызова; отдельный модуль ради «красоты».

## Конкурентность и жизненный цикл
- Структурная конкурентность: запуск агента в `viewModelScope`, отмена = отмена `Job`; сеть и текущий инструмент останавливаются вместе с ним.
- Диспетчеры не хардкодим (`DispatcherProvider` из ядра), в тестах подставляем тестовые. Фактически сейчас `Dispatchers.IO` используется напрямую в сетевых адаптерах (`:data:llm`, `:data:auth`) и `SearchFilesTool`.
- `runBlocking` и `GlobalScope` в основном коде запрещены.
- Убийство процесса во время ответа: незавершённый ход помечается прерванным, история остаётся целой (проверяется на этапе 5).
- Фоновая работа (foreground service, WorkManager) в MVP не нужна. Когда понадобится, `AgentLoop` запускается из сервиса без изменений.

## DI и композиция
- Hilt (рекомендация Google, проверка на этапе компиляции), KSP.
- **Модули без Android (`:core:domain`, `:data:llm`) не содержат DI-аннотаций.** Классы создаются обычными конструкторами, связывание — `@Provides` в `:app/di/`.
- Android-модули (`:tools`, `:data:auth`) могут использовать Hilt и регистрировать свои классы сами (`@Binds @IntoSet`, `@IntoMap`).
- Конфигурация: константы бэкенда и входа лежат в своих объектах (`BackendProfile` в `:data:llm`, `AuthConfig` в `:data:auth`) и берутся из `docs/backend-notes.md`. Понятие «AppConfig» из ТЗ означает именно эту пару плюс лимиты инструментов.
