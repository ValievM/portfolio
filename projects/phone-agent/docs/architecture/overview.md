## Цель и принципы

Цель: чтобы новая возможность добавлялась **новым файлом + одной строкой регистрации**, а не правкой десяти мест.

Принципы (по важности):
1. **Правило зависимостей.** Всё зависит от ядра (domain), ядро не зависит ни от чего. Ядро — чистый Kotlin, без Android, сети и БД.
2. **Порты и адаптеры.** Всё, что общается с внешним миром (модель, хранилище, телефон, пользователь), спрятано за интерфейсом в ядре. Реализации меняются, ядро нет.
3. **Открыто для расширения, закрыто для правки.** Новый инструмент, способ входа, бэкенд модели, экран добавляются без изменения цикла агента.
4. **Нестабильное изолируем.** Бэкенд подписки закрытый и может меняться. Его формат живёт только в одном модуле и не течёт дальше (anti-corruption layer).
5. **Ошибки — данные.** Ожидаемые сбои (нет сети, 401, отказ пользователя) — это типы, а не исключения.
6. **Правила проверяет машина.** Границы держатся не на дисциплине, а на Gradle и архитектурных тестах.
7. **Разработка через тесты (TDD).** Логика пишется от теста: красный → зелёный → рефакторинг ([testing.md](testing.md)). Архитектура это обеспечивает: ядро чистое, у портов есть фейки, Android-вызовы вынесены в тонкие обёртки, поэтому тест пишется до кода и не требует телефона.
8. **Простота по умолчанию.** Вводим ровно столько структуры, сколько нужно сегодня, но швы (интерфейсы) закладываем сразу.

**Чего не делаем (сознательно):** полный DDD (агрегаты, доменные события, bounded contexts), CQRS, event sourcing, use case на каждый чих, базовые классы вроде `BaseViewModel`, Service Locator, RxJava, LiveData, XML-вёрстка, KMP «на всякий случай», модуль на каждый инструмент. Причина: проект одиночный и MVP, лишняя церемония тормозит и ломает читаемость. Это согласуется с рекомендациями Google (доменный слой опционален, не дробить модули слишком мелко).

## Общая картина

```
                ┌─────────────────────────── :app (composition root) ───────────────────────────┐
                │  UI (Compose) ─ ViewModel ─┐        DI (Hilt) собирает всё                    │
                │  Room / DataStore адаптеры │        UserInteractionBridge (диалоги, разрешения)│
                └───────┬───────────────┬────┼─────────────────┬──────────────┬─────────────────┘
                        │               │    │                 │              │
                   :tools          :data:auth │            :data:llm           │
              (alarm, files,     (входы, токены,        (Responses API,        │
                 notify)          Keystore)             SSE, DTO, ACL)         │
                        │               │    │                 │              │
                        └───────────────┴────┴───────┬─────────┴──────────────┘
                                                     ▼
                                   :core:domain (чистый Kotlin, JVM)
              AgentLoop · Tool · ToolPipeline · порты · модели · ошибки · политики
```
Стрелка всегда к `:core:domain`. Ни один адаптер не знает о другом адаптере.

## Модули

### MVP-набор (создаём на этапе 1)

| Модуль | Тип | Что внутри | Зависит от |
|---|---|---|---|
| `:core:domain` | Kotlin JVM | модели, порты, `AgentLoop`, `Tool`, конвейер инструментов, ошибки, политики; `testFixtures` с фейками портов | только kotlin-stdlib, coroutines, kotlinx-serialization-json |
| `:data:llm` | Kotlin JVM | клиент Responses API: OkHttp, SSE, DTO, мапперы, `BackendProfile` | `:core:domain` |
| `:data:auth` | Android lib | способы входа, PKCE, JWT, `TokenStore` (Keystore), обновление токена, `SessionManager` | `:core:domain` |
| `:tools` | Android lib | инструменты `alarm`, `notify`, `files` + Hilt-регистрация | `:core:domain` |
| `:app` | Android app | UI, навигация, Room/DataStore-адаптеры, `UserInteractionBridge`, DI | все |

Почему так: `:core:domain` и `:data:llm` — чистая JVM, поэтому тесты идут за секунды и Android случайно туда не проникнет. `:tools` — граница плагинов. `:data:auth` — самый чувствительный код, ему нужен свой периметр. UI и Room пока лежат в `:app`, по пакетам.

### Правило роста

Выделяем новый модуль, только когда есть **хотя бы одна** причина: второй потребитель кода; своя пачка зависимостей и тестов; сборка `:app` стала заметно медленной; код хочется закрыть `internal`. Первые кандидаты: `:data:chat` (Room), `:feature:*` (экраны), `:core:ui` (тема и компоненты), отдельные модули для тяжёлых инструментов.

### Инфраструктура сборки
- Версии зависимостей: `gradle/libs.versions.toml`.
- Общие настройки модулей: convention plugins в `build-logic/` (чтобы не копировать конфиг по модулям).
- В библиотечных модулях включён `explicitApi()`: каждое объявление явно `public` или `internal`. По умолчанию всё `internal`.
